Technical details & live demo

What I built

  • MAJOR.MINOR.PATCH semantic versioning for agent registration and tenant-specific configuration changes.
  • Configuration version diffs (e.g. 1.0.0 vs 1.1.0) that flag added, modified and deleted records before promotion, plus environment-specific field highlighting with wildcard JSON paths.
  • Tenant-centric promotion: deploy and validate in a lower environment, then promote to higher — with batch-level versioning so the validated version is the promoted version.
  • Fleet-wide agent version change: one request moves every tenant on the old version to the new one through a single shared deployment, with per-tenant config overrides and retry-safe reuse.
  • Batch rollback settlement that restores state on failure without overwriting changes made since.
  • Revision-numbering and record-selection rules extracted into small, pure, unit-tested modules shared across services.

Read the case study
Context

The platform deploys agents to multiple environments for multiple tenants. Several tenants can share one agent deployment, and environments promote from a base environment upward.

Challenge

Upgrading an agent version, rolling back a promotion and showing accurate status all get hard when deployments are shared. Published batches are immutable, revision numbers must stay unique, and failures can happen after a change has already merged.

What I did
  • Version change. Revise every affected tenant mapping, copy or override config, upgrade the same release in place, deploy through one shared plan, fan status out to all participants, and keep the whole flow retry-safe.
  • Rollback. Settle a run only when all its records finish. On failure, restore batch statuses and plan stamps, but never overwrite a mapping that has moved on.
  • Consistency. Revision numbering bumps the major on promotion and the minor otherwise, taking the next free minor on a collision. One rule decides which deployment record a row shows. Domain logic lives in pure modules with dedicated tests.
  • Developer-facing features. Config diff, environment-specific field highlighting with array wildcards, and config-name auto-generation.
Outcome

Merged into the shared codebase and covered by unit tests. No production metrics to report publicly.

What I learned

Modelling immutable revisions, state machines across shared resources, safe retries and rollbacks, and pure, testable domain logic in a layered FastAPI codebase.

Technical details & live demo

RAG (retrieval-augmented generation) means the system first retrieves the most relevant passages from your documents, then asks the AI model to answer using only those passages.

RAG pipeline6 stages
  2. DocumentsPDF · DOCX · CSV
  3. Parseclean text
  4. Chunksize + overlap
  5. Embedembeddings
  6. Retrievetop-k
  7. Grounded answerwith sources
  1. 01

    Parse

    Turn PDFs, DOCX, CSV, JSON and text into clean text with metadata. Same problem I solved in unified-file-reader.

  2. 02

    Chunk

    Split documents by size and overlap. Too small loses context; too large dilutes relevance. I tune both per corpus.

  3. 03

    Embed

    Generate embeddings for every chunk and keep chunk ↔ source mapping for citations.

  4. 04

    Index

    Store vectors in FAISS or ChromaDB depending on the deployment need.

  5. 05

    Retrieve

    Top-k similarity search for the query; retrieval quality is measured, not assumed.

  6. 06

    Generate

    Context-aware LLM response grounded in the retrieved chunks, with sources the user can check.

How I work

Spec first, agents second, review always

I use AI coding agents (Claude Code, Devin, Google Antigravity) every day. A written spec and a careful review keep the output clean.

  1. SpecWrite what it must do and how we'll know it works.
  2. PlanAn agent drafts the plan; I own the structure and data contracts.
  3. BuildAgents implement small modules; subagents take parallel tasks.
  4. VerifyLinting, unit and regression tests, then a human review.
  5. ShipSmall changes that are easy to roll back.
